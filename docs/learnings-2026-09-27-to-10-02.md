# What we learned, 27 Sep – 2 Oct 2026

This covers the customer journey, the automatic document checks, the two-bureau credit detail and the income detail. It records how the work went, not just what was built. Each lesson says what happened, then what we do differently now.

## How we work

**1. A database change isn't live until the live database says so.**
Migrations 049, 050 and 051 were marked "done", but they had never run on Supabase. Nobody noticed until a staff user clicked "Open" on a file and got `sign-in required`. The file service was calling a privacy check that didn't exist. The same gap meant the demo login could see real customers.
*Now:* after each migration, ask the live database whether a new function exists: `PGRST202` means missing, `42501` means it exists. The run log records only what was checked.

**2. Usage limits, not bugs, cost the most time.**
Four multi-agent runs died mid-way when the plan's usage limit hit. Two of them died before writing a single file. Work in progress inside a run is lost, and a run can only be resumed inside the same session.
*Now:* long builds are done one step at a time, saving to disk and to git after each step, so a limit costs minutes, not the build. Multi-agent runs are kept for when the extra checking clearly pays for itself.

**3. The independent review caught real bugs.**
- The judged design panel caught that the existing tests depended on two particular test PANs.
- The four reviewers found three real maths bugs in the bureau combining. One was a live loan disappearing from the totals when the other bureau showed it as settled.
- A reviewer also found an older crash in the credit engine: a customer with no record at either bureau broke the assessment. About 60 of the 2,000 synthetic customers would have hit it.

*Now:* new data shapes (no-hit, two bureaus, missing fields) get a deliberate "what breaks downstream" check before the data generator runs.

**4. Keep the engine's contract and add around it.**
The credit engine reads exactly one bureau row per application. We kept that row, now the combined worst-of figures, and put the two bureaus' detail in new tables. The engine, rate grid and FOIR needed no change, and every old test stayed green.

**5. Tests that depend on today's date eventually fail.**
A test policy dated 1 Oct 2026 became "in force" on 1 Oct, and three tests failed for no code reason. Test dates now sit in 2099.

**6. Policy questions get a safe default and a switch, not a wait.**
Five bureau policy points were built with the cautious option, each behind one switch:
- the score comes from CIBIL;
- 5% of card balances counts as an obligation;
- cards count as active accounts;
- guarantor late payments count;
- late payments at a lender whose licence was cancelled count.

The build carried on, and the decisions stay easy to change.

## Technical lessons

**7. Postgres regex:** `\y` is a word boundary; `\b` means backspace. A pay-month parser silently returned nothing because of it.

**8. Don't pass code through shell heredocs or Python string escapes.** Backslashes were mangled twice, and one `sed` wrecked a whole function. Files are now written with the editor tools.

**9. `window.open(url, "_blank", "noopener")` returns null.** A tab can't be filled in after a wait, and the second try gets blocked as a pop-up. Open the tab first without `noopener`, cut its `opener` by hand, then load the file.

**10. Readers that wait on a background job must keep looking.** Step 4 checked for document readings once, when the page opened. If the documents were still being read, nothing was filled and nothing said why. It now re-checks for a minute, and has a "Fill from my documents" button that shows its errors.

**11. Downloaded e-Aadhaar and e-PAN PDFs don't print "Label: value" pairs.** The form reader missed gender, date of birth, father's name and most of the address. Reading line by line fixed it. Separately, AWS's reader started rejecting some unlocked PDFs. That is still open (P1).

**12. Real application numbers are 12 digits; the test data used `APP-…`.** All customer uploads failed until the ID check accepted both. Test with the real shape of IDs, not just the sample shape.

**13. Logins added by an admin have no password.**
- Supabase's "Signups not allowed for otp" means no login exists for that email at all.
- The password sign-in also has to ignore a stray space or capital letter in the email.

## Data and privacy

**14. Your own documents are real personal data.** A request to re-read your Aadhaar through the reader was refused, correctly. All checks on your files were done by field names and shapes only, never values.

**15. Cloud mode only sees the git repo.** The Vault design notes, the memory notes and working files aren't there, so it suits self-contained jobs (a code review, a long test run), not builds that lean on those notes.

## Added 2 Oct, night

**16. Rule out the test method before blaming the system.**
The "AWS rejects your PDFs" problem (P1) was never real. My re-run loop passed each request inline through the shell, which mangled it, and AWS answered "invalid parameters". Sent as a file, every document read first time. A day was lost treating it as an AWS fault.
*Now:* when a failure appears only in a manual test, retry with a cleaner input path (a file, not inline shell text) before changing code.

**17. Running the full journey at volume finds bugs that single tests don't.**
The first batch of 250 synthetic customers came out 74% referred. That exposed two problems:
- the income check compared take-home pay with Form 16, which is gross pay, and would have hit real customers too;
- the generator itself chose cars too expensive for the salary.

*Now:* every new data feature gets a volume dry run, and the outcome mix is checked against what a real lender would expect.

**18. Hand off live database steps in small, checkable pieces.**
The synthetic data went live in 8 small batches and 3 disbursal runs. Each printed its own counts, so a timeout would have cost one batch. A single read-only check query then confirmed the totals.
